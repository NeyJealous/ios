ТЗ ДЛЯ CODEX
v2.2 — Stabilization, Synchronization & Investment Universe

Главная цель:
Стабилизировать архитектуру проекта перед дальнейшим развитием Investment Operating System.

До начала разработки следующих крупных модулей необходимо:
- стабилизировать синхронизацию;
- разделить ядро данных;
- оптимизировать скорость работы;
- устранить лишние API-запросы;
- создать автоматическую Инвестиционную вселенную;
- исключить ложные рекомендации;
- добавить журнал изменений инвестиционной вселенной.

ВАЖНО:
Не добавлять новую инвестиционную логику, пока не стабилизирована текущая архитектура.
Сначала привести синхронизацию, кэш, ядро расчетов и зависимости листов в порядок.

────────────────────────────
I. Архитектура данных
────────────────────────────

Проект должен быть построен вокруг единого потока данных:

API
↓
Данные источников
↓
Справочник инструментов
↓
Инвестиционная вселенная
↓
Факты
↓
Признаки
↓
Оценки
↓
Решения
↓
Советник / План сделок / Главная

Никакой пользовательский лист не должен обращаться к API напрямую.

Нельзя, чтобы:
- Советник напрямую ходил в API;
- Главная сама считала сложную бизнес-логику;
- План сделок сам определял стратегию;
- Ребалансировка брала данные из визуальных листов.

────────────────────────────
II. Справочник инструментов
────────────────────────────

Создать единый автоматический справочник инструментов.

Справочник — это максимально полный каталог известных системе инструментов.

Пока в целевой инвестиционной вселенной используются только:
- акции;
- облигации;
- фонды.

Справочник:
- не принимает инвестиционных решений;
- не формирует рекомендации;
- не должен заполняться вручную;
- обновляется автоматически из API;
- хранит все известные системе инструменты, включая неактивные.

Источники:
- T-Invest Instruments API;
- MOEX ISS при необходимости.

Новые поля для справочника:
- FIGI;
- UID;
- ISIN;
- Тикер;
- Название;
- Тип инструмента;
- Подтип;
- Валюта;
- Лотность;
- Дата листинга;
- Источник данных;
- Дата последней проверки;
- Статус инструмента;
- Доступен неквалифицированному инвестору;
- Стратегически доступен;
- Торгуется сейчас;
- Можно купить сейчас;
- Причина временной недоступности;
- Причина исключения;
- Последняя проверка.

Важное правило:
Никогда автоматически не удалять инструменты из справочника.

Если бумага исчезла из API, стала недоступной, погашена или архивирована — она должна получить соответствующий статус, но остаться в справочнике.

Причина:
Это нужно для сохранения истории сделок, FIFO, налогового учета, старых операций и воспроизводимости портфеля.

────────────────────────────
III. Инвестиционная вселенная
────────────────────────────

Добавить новый лист:

Инвестиционная вселенная

Именно этот лист становится источником для:
- Company Rating;
- Bond Engine;
- Advisor;
- Decision Engine;
- Portfolio Health;
- Trade Plan;
- Rebalance.

Инвестиционная вселенная — это не весь справочник, а список инструментов, которые подходят текущей стратегии.

Очень важно:
Инвестиционная вселенная ≠ инструменты, которые торгуются прямо сейчас.

Это два разных понятия.

────────────────────────────
IV. Три уровня доступности инструмента
────────────────────────────

Система должна разделять три уровня доступности.

1. Известен системе

Инструмент находится в Справочнике.

2. Подходит стратегии

Инструмент попадает в Инвестиционную вселенную.

3. Можно купить прямо сейчас

Инструмент доступен для покупки в текущий момент и может попасть в План сделок.

Пример:
Сегодня суббота.
Торгуется сейчас = Нет.
Можно купить сейчас = Нет.
Стратегически доступен = Да.
Инвестиционная вселенная = Да.
Советник продолжает анализировать инструмент.

────────────────────────────
V. Стратегическая и временная доступность
────────────────────────────

Нужно разделить два статуса:

1. Стратегически доступен

Показывает, может ли неквалифицированный инвестор покупать инструмент в принципе.

Если Стратегически доступен = Да, инструмент остается в Инвестиционной вселенной, даже если сегодня:
- суббота;
- воскресенье;
- праздничный день;
- ночь;
- торговая сессия закрыта;
- биржа временно не торгует.

2. Торгуется сейчас

Это временный статус.
Он используется только для операционного плана покупки.

Торгуется сейчас = Нет не является причиной исключения из Инвестиционной вселенной.

3. Можно купить сейчас

Можно купить сейчас = Да только если:
- Стратегически доступен = Да;
- Торгуется сейчас = Да;
- брокер разрешает покупку;
- есть актуальная цена / торговая сессия / возможность выставить заявку.

────────────────────────────
VI. Когда исключать инструмент из Инвестиционной вселенной
────────────────────────────

Исключать инструмент из Инвестиционной вселенной можно только если:
- инструмент требует статус квалифицированного инвестора;
- инструмент архивный;
- облигация погашена;
- бумага исключена из обращения;
- тип инструмента не входит в текущую стратегию;
- инструмент больше недоступен через брокера;
- инструмент явно запрещен правилами стратегии;
- инструмент имеет ручной запрет на покупку.

Нельзя исключать инструмент только потому, что:
- сегодня выходной;
- рынок закрыт;
- торговая сессия не идет;
- временно нет торгов;
- нет текущей котировки в момент синхронизации.

────────────────────────────
VII. Universe Diff — журнал изменений Инвестиционной вселенной
────────────────────────────

Добавить новый лист:

Изменения инвестиционной вселенной

или техническое название:
Universe Diff

Назначение:
При каждой полной синхронизации система должна не просто обновлять справочник и Инвестиционную вселенную, а фиксировать изменения.

Фиксировать:
- какие инструменты появились впервые;
- какие инструменты стали доступны неквалифицированному инвестору;
- какие инструменты стали недоступны неквалифицированному инвестору;
- какие инструменты были переведены в архив;
- какие облигации погашены;
- какие инструменты изменили статус;
- какие инструменты были исключены из Инвестиционной вселенной;
- причину исключения;
- дату изменения;
- источник изменения.

Поля листа:
- Дата изменения;
- Тикер;
- ISIN;
- FIGI / UID;
- Название;
- Тип инструмента;
- Старый статус;
- Новый статус;
- Старое значение “Стратегически доступен”;
- Новое значение “Стратегически доступен”;
- Старое значение “Доступен неквалифицированному инвестору”;
- Новое значение “Доступен неквалифицированному инвестору”;
- Причина изменения;
- Источник данных;
- Комментарий.

Важное правило:
Изменения должны фиксироваться как события.
Нельзя молча удалять или скрывать инструмент без записи в Universe Diff.

Цель:
Пользователь должен понимать, почему бумага появилась, исчезла из рекомендаций или изменила статус.

────────────────────────────
VIII. Архитектура синхронизации
────────────────────────────

Разделить синхронизацию на три режима:

1. Быстро обновить портфель
2. Полная синхронизация данных
3. Пересчитать рекомендации

────────────────────────────
IX. Быстрая синхронизация
────────────────────────────

Назначение:
Ежедневное быстрое обновление.

Что обновлять:
- счета;
- текущие позиции;
- свободные деньги;
- текущие цены;
- стоимость портфеля;
- Главная;
- Здоровье портфеля;
- Советник;
- План сделок.

Что НЕ трогать:
- полную историю сделок;
- справочник инструментов;
- инвестиционную вселенную;
- параметры облигаций;
- факты;
- признаки;
- старые операции;
- полную аналитику;
- Universe Diff.

Принцип:
Быстрая синхронизация должна работать максимально быстро и использовать уже имеющиеся данные на листах.

────────────────────────────
X. Полная синхронизация данных
────────────────────────────

Назначение:
Редкое техническое обновление.

Что обновлять:
- счета;
- сделки;
- операции;
- портфель;
- справочник инструментов;
- инвестиционную вселенную;
- Universe Diff;
- параметры акций;
- параметры облигаций;
- купоны;
- дивиденды;
- данные источников;
- факты;
- признаки;
- оценки;
- режим рынка;
- индекс возможностей;
- здоровье портфеля;
- советник;
- план сделок.

Когда запускать:
- вручную;
- раз в неделю;
- после крупных изменений;
- после добавления нового счета;
- после добавления новых инструментов;
- после ошибки “инструмент не найден”;
- после изменения правил отбора Инвестиционной вселенной.

────────────────────────────
XI. Пересчитать рекомендации
────────────────────────────

Назначение:
Пересчет без API.

Что делать:
- не обращаться к T-Invest;
- не обращаться к Мосбирже;
- не обращаться к ЦБ;
- использовать только уже загруженные данные;
- пересчитать:
  - оценки;
  - решения;
  - ребалансировку;
  - здоровье портфеля;
  - советник;
  - план сделок;
  - главную.

Это должна быть самая безопасная и быстрая операция.

────────────────────────────
XII. Как не упираться в лимиты
────────────────────────────

Перед любым API-запросом сначала проверить:
1. есть ли данные на листе;
2. есть ли актуальный кэш;
3. когда данные были обновлены;
4. истек ли TTL;
5. действительно ли нужно обновление.

Запрещено:
- дергать API по каждой строке;
- дергать API по каждому тикеру отдельно, если можно батчем;
- обновлять весь справочник при каждом запуске;
- пересчитывать все листы после каждого маленького изменения;
- читать и писать ячейки по одной;
- полностью очищать листы без необходимости;
- перезаписывать историю без необходимости.

Обязательно:
- читать диапазоны через getValues();
- писать диапазоны через setValues();
- собирать данные в Map/Object в памяти;
- делать один проход по данным;
- писать результат пачкой;
- использовать LockService, чтобы не запускались две синхронизации одновременно;
- хранить timestamps обновления;
- хранить курсоры последней синхронизации;
- использовать upsert по ключу;
- использовать частичное обновление;
- использовать incremental sync.

────────────────────────────
XIII. Инкрементальная загрузка сделок
────────────────────────────

Лист “Сделки” должен быть историческим источником.

Нельзя каждый раз загружать все сделки заново.

Нужно:
- хранить дату / ID последней загруженной операции;
- при синхронизации запрашивать только новые операции;
- проверять дубли по уникальному ключу;
- не перезаписывать старую историю без необходимости.

Источник истины для истории:
Сделки.

────────────────────────────
XIV. Ядро расчетов
────────────────────────────

В проекте не должно быть одного “главного пользовательского листа”.

Нужно разделить ядро по типам данных.

Главные источники истины:

1. Сделки
История операций.
Неизменяемая база для FIFO, доходов, налогов и исторического анализа.

2. Портфель
Текущее состояние позиций.
Ядро для Главной, Здоровья портфеля, Ребалансировки, Советника и Плана сделок.

3. Счета
Список счетов и признак “включать в общий портфель”.

4. Стратегии счетов
Связь счета и стратегии.
Критически важно: связывать не по русскому названию, а по ID счета.

5. Справочник инструментов
Полный каталог известных системе инструментов.

6. Инвестиционная вселенная
Список инструментов, подходящих для анализа и рекомендаций.

7. Данные источников
Сырые данные из API.

8. Факты
Нормализованные объективные данные.

9. Признаки
Интерпретация фактов.

10. Оценки
Результаты скоринга.

11. Решения
Итоговые рекомендации Decision Engine.

12. Изменения инвестиционной вселенной
История изменения доступности и состава Инвестиционной вселенной.

13. Главная / Советник / План сделок
Не источник истины.
Это только пользовательское представление результата.

────────────────────────────
XV. Что оптимизировать в текущем проекте
────────────────────────────

1. Связи счетов и стратегий
Сейчас есть риск ошибки из-за названий вроде “Пассивный” / “Пасивный”.
Нужно перейти на ID.

2. Здоровье портфеля
Сейчас оно может не видеть позиции из листа “Портфель”.
Проверить фильтр активных счетов и связь счета со стратегией.

3. Ребалансировка
Не показывать “Сократить на 0.00”.
Если сумма нулевая — не создавать рекомендацию.

4. Советник
Не показывать пустые тикеры, “00”, технические строки и рекомендации на 0 рублей.

5. План сделок
Не создавать строки без тикера, если это конкретная сделка.
Групповые рекомендации хранить отдельно.

6. Рейтинг компаний
Не давать рейтинг “Покупать по плану”, если нет фундаментальных данных.
Если данных мало — статус “Недостаточно данных”.

7. Анализ облигаций
Если нет доходности, дюрации, купона, даты погашения — статус “Недостаточно данных”.
Такие бумаги не должны попадать в топ.

8. Даты
Исправить отображение числовых дат.
Пользователь должен видеть обычный формат даты.

9. Кэш
Пользователь не должен видеть слово “Кэш”.
В интерфейсе показывать:
- “Данные обновлены”;
- “Источник”;
- “Данные устарели”.

10. Технические ID
Скрыть Rule_ID, Feature_ID, FIGI, UID, Account_ID, Strategy_ID в пользовательских листах.

────────────────────────────
XVI. Техническая оптимизация Apps Script
────────────────────────────

Нужно проверить весь проект на:
- getRange() внутри циклов;
- setValue() внутри циклов;
- appendRow() в больших циклах;
- повторное чтение одного и того же листа;
- повторные API-запросы;
- полную очистку листов без необходимости;
- пересчет всех модулей после частичного обновления.

Заменить на:
- batch read;
- batch write;
- in-memory maps;
- upsert по ключу;
- частичное обновление;
- timestamps;
- кэш;
- режимы sync.

────────────────────────────
XVII. Главный принцип
────────────────────────────

Главная, Советник и План сделок не должны быть ядром расчетов.

Они должны быть витриной.

Ядро расчетов:
Портфель + Сделки + Счета + Стратегии счетов + Справочник + Инвестиционная вселенная + Факты + Признаки + Оценки + Решения + Universe Diff.

────────────────────────────
XVIII. Итоговая задача
────────────────────────────

Перед дальнейшим развитием IOS нужно стабилизировать:
- синхронизацию;
- зависимости листов;
- ядро расчетов;
- кэш;
- скорость обработки;
- корректность рекомендаций;
- справочник инструментов;
- инвестиционную вселенную;
- журнал изменений инвестиционной вселенной;
- отсутствие ложных сигналов “Покупать”.

После завершения этой версии система должна:
- автоматически поддерживать полный каталог доступных акций, облигаций и фондов для неквалифицированного инвестора;
- автоматически формировать Инвестиционную вселенную;
- не исключать инструменты из-за выходных, праздников или закрытой торговой сессии;
- отделять постоянную доступность инструмента от временного торгового статуса;
- фиксировать все изменения Инвестиционной вселенной в Universe Diff;
- не выполнять лишних API-запросов;
- быстро обновлять только изменившиеся данные;
- использовать единое ядро данных для всех расчетов;
- обеспечивать масштабируемость для будущего добавления Knowledge Engine, Portfolio Intelligence, One Click Execution и автоматической торговли.

Только после этого переходить к новым модулям Knowledge Engine, Portfolio Intelligence и One Click Execution.
