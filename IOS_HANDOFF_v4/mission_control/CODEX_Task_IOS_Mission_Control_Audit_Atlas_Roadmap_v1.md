# ЗАДАЧА ДЛЯ CODEX
# IOS Mission Control: аудит, машинный реестр, визуальный атлас и Roadmap

## Роль

Ты выступаешь как:

- архитектор Apps Script;
- аналитик текущего кода;
- специалист по визуализации архитектуры;
- инженер документации;
- специалист по Figma-ready SVG;
- разработчик автоматизируемого реестра проекта.

## Главная цель

На основании:

1. текущего архива проекта;
2. Master Specification v3.0;
3. существующих карт и roadmap SVG;
4. фактической структуры Google Sheets (если доступна через MCP);

создать достоверный `IOS Mission Control`.

Не ограничивайся красивой схемой. Сначала выполни аудит, затем визуализацию.

---

# 1. Жёсткие ограничения

## Запрещено

- придумывать проценты готовности;
- считать файл доказательством завершения модуля;
- менять инвестиционную логику;
- менять код Apps Script до завершения аудита;
- удалять `.gs` или `.js` без отдельного решения пользователя;
- смешивать целевую и фактическую архитектуру;
- выводить секреты, токены или содержимое PropertiesService;
- показывать пользователю технические ID на пользовательских картах;
- объявлять тесты пройденными без фактического запуска;
- делать Figma единственным источником статусов.

## Обязательно

- все выводы подтверждать файлом, функцией, листом или тестом;
- неизвестное состояние помечать «Неизвестно»;
- каждому статусу указывать источник и уровень уверенности;
- сохранить исходный проект без изменений на этапе аудита;
- вести журнал найденных расхождений;
- использовать только русский пользовательский интерфейс.

# 3. Этап 1 — безопасная подготовка

1. Распакуй архив в отдельную рабочую папку.
2. Не изменяй оригиналы.
3. Зафиксируй:
   - дату архива;
   - количество файлов;
   - количество `.gs`;
   - количество `.js`;
   - количество HTML;
   - наличие `.clasp.json`;
   - наличие `appsscript.json`.
4. Создай `audit/input_inventory.json`.
5. Создай `audit/input_inventory.md`.

Отдельно зафиксируй конфликт:

- в проекте одновременно присутствуют `.gs` и `.js` версии многих модулей;
- не принимай решение об удалении;
- создай отдельную запись риска `RISK-FILE-DUALITY-001`.

- потенциальные вызовы внутри циклов:

# 7. Этап 5 — проверка Google Sheets через MCP

Если MCP доступен:

1. Получи список листов.
2. Получи заголовки.
3. Получи размеры диапазонов.
4. Определи скрытые листы.
5. Не читай секретные значения.
6. Сопоставь листы со спецификацией.
7. Проверь пользовательский интерфейс:
   - русский язык;
   - отсутствие FIGI/UID/Account_ID/Strategy_ID на пользовательских листах;
   - отсутствие пустых тикеров;
   - отсутствие технических сообщений;
   - даты;
   - рекомендации на 0;
   - рекомендации с 0 лотов.

Создай:

- `registry/live_sheets.json`;
- `audit/sheets_gap.md`;
- `audit/ux_findings.md`.

Если MCP недоступен:

- не симулируй результат;
- поставь `verification_status = not_checked`;
- создай раздел «Требуется проверка через MCP».

# 8. Этап 6 — проверка синхронизации

Найди фактические entry points для:

1. Быстрой синхронизации.
2. Полной синхронизации.
3. Пересчёта без API.

Для каждого режима построй последовательность вызовов.

Проверь:

- есть ли LockService;
- есть ли повторные API;
- есть ли чтение/запись в циклах;
- какие листы обновляются;
- используется ли инкрементальная история;
- хранятся ли курсоры/timestamps;
- можно ли реально выполнить пересчёт без API.

Создай:

- `audit/sync_fast.mmd`;
- `audit/sync_full.mmd`;
- `audit/sync_recalc.mmd`;
- `audit/synchronization_findings.md`.

Не называй режим реализованным, пока цепочка не подтверждена кодом и тестом.

---

# 9. Этап 7 — проверка инвестиционной логики

Не изменяй формулы.

Проверь только соответствие архитектуре:

- рекомендации создаются только через Decision Engine;
- Company Rating не формирует самостоятельную покупку;
- Bond Engine не формирует самостоятельную покупку;
- статус «Недостаточно данных» блокирует покупку;
- Reserve Engine имеет приоритет при дефиците резерва;
- Coupon Ladder не покупает слабую облигацию только ради месяца;
- целевые доли берутся из выбранной стратегии;
- нет фиксированных весов, если спецификация требует настройки;
- многосчётная связь использует Account ID;
- нет нулевых рекомендаций.

Создай:

- `audit/investment_logic_findings.md`;
- `registry/decision_rules.json`.

# 10. Этап 8 — расчёт достоверной готовности

Для каждого модуля рассчитай готовность только при наличии данных.

Вес:

- реализация — 35%;
- тесты — 20%;
- документация — 15%;
- интеграция — 15%;
- проверка в рабочей таблице — 15%.

Если рабочая таблица недоступна:

- не нормализуй шкалу до 100%;
- показывай, например:
  - `confirmed_score: 65/85`;
  - `live_verification: not_checked`;
  - `display_status: Требуется проверка`.

Создай `registry/status.json`.

1. Что реально найдено.
2. Что подтверждено.
3. Что не подтверждено.
4. Где спецификация расходится с кодом.
5. Где код расходится с таблицей.
6. Критические риски.
7. Быстрые улучшения.
8. Рекомендуемый порядок работ.
9. Список созданных файлов.

# 16. Definition of Done

Задача завершена, если:

- оригинальный проект не изменён;
- создан полный машинный реестр;
- выполнен аудит `.gs/.js`;
- построена матрица требований;
- Target и Current Architecture разделены;
- создано не менее 21 SVG-карты;
- создан локальный интерактивный HTML;
- создан пакет импорта в Figma;
- готовность не выдумана;
- все неизвестные состояния явно отмечены;
- создан приоритизированный Roadmap;
- результаты можно повторно сгенерировать после изменения проекта.
