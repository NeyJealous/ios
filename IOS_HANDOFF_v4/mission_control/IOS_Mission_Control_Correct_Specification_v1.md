# Investment Operating System (IOS)
# Спецификация визуального центра управления проектом
## Версия 1.0

Статус: рабочая спецификация для реализации в Figma/FigJam и локальном репозитории.

---

# 1. Назначение

Создать единый визуальный центр управления проектом IOS, который позволяет без чтения десятков TXT/MD-файлов увидеть:

- целевую архитектуру;
- фактическое состояние проекта;
- зависимости между модулями;
- порядок разработки;
- текущие риски и технический долг;
- готовность этапов;
- ближайшие задачи;
- связь документации, кода, листов, тестов и релизов.

Визуальный центр должен быть удобен:

- на ПК;
- на iPhone;
- в Figma;
- в FigJam;
- при экспорте в SVG/PDF/PNG;
- для работы Codex и субагентов.

Главный принцип:

> Атлас и Roadmap не должны выдавать желаемое состояние за фактически реализованное.

# 2. Канонический формат

## 2.1 Основная программа

Основной формат — Figma.

Причины:

- удобный просмотр на ПК и iPhone;
- масштабирование большой карты;
- страницы, фреймы и компоненты;
- ссылки между картами;
- комментарии;
- возможность редактирования;
- экспорт в SVG, PNG и PDF.

## 2.2 Дополнительные форматы

Обязательно поддерживать:

- SVG — для импорта и резервной копии;
- HTML — для просмотра вне Figma;
- PNG — для быстрых превью;
- PDF — для печати и офлайн-просмотра;
- JSON/CSV — для машинного реестра статусов и зависимостей.

Figma является визуальным представлением, но не источником истины.

# 3. Источники истины

Визуальный центр строится только на основании:

1. Master Specification.
2. Фактического кода Apps Script.
3. Фактической структуры Google Sheets.
4. Результатов тестов и диагностики.
5. RFC/ADR.
6. Roadmap и Project History.
7. Аудита текущего проекта.

Запрещено выставлять готовность модулей на основании только наличия файла с похожим названием.

Например:

- наличие `BondEngine.gs` не означает, что Bond Engine завершён;
- наличие `DecisionEngine.gs` не означает отсутствие ложных рекомендаций;
- наличие `SmokeTests.gs` не означает, что тесты проходят;
- наличие `DataCache.gs` не означает, что все модули используют корректный TTL.

# 4. Модель статуса

Для каждого модуля, листа, требования и этапа используются отдельные поля:

## 4.1 Статус реализации

- Не начато.
- Запланировано.
- В работе.
- Реализовано частично.
- Реализовано.
- На проверке.
- Заблокировано.
- Требует рефакторинга.
- Устарело.
- Не применимо.

## 4.2 Статус проверки

- Не проверено.
- Проверено статически.
- Smoke Test пройден.
- Интеграционный тест пройден.
- Проверено в рабочей таблице.
- Проверка не пройдена.

## 4.3 Статус документации

- Нет спецификации.
- Черновик.
- Утверждено.
- Требует актуализации.
- Соответствует коду.
- Не соответствует коду.

## 4.4 Уровень уверенности

- Высокий — подтверждено кодом, таблицей и тестом.
- Средний — подтверждено кодом, но не тестом.
- Низкий — основано на названии файла или старом описании.
- Неизвестно — данных недостаточно.

## 4.5 Процент готовности

Процент не заполняется вручную и не выводится без расчётной методики.

Допустимая формула:

Готовность =
- 35% реализация;
- 20% тесты;
- 15% документация;
- 15% интеграция;
- 15% пользовательская проверка.

Если один из компонентов неизвестен, вместо процента показывается «Требуется аудит».

- параллельное наличие `.gs` и `.js` версий значительной части проекта;

# 6. Цветовая система

- Синий — данные и Data Flow.
- Зелёный — инвестиционная логика.
- Оранжевый — синхронизация и процессы.
- Фиолетовый — инфраструктура и разработка.
- Красный — пользовательский интерфейс и критические ошибки.
- Жёлтый — Decision Engine, контрольные точки и релизы.
- Серый — внешние источники и неизвестное состояние.

Цвет не может быть единственным носителем статуса.

Обязательно использовать текстовую метку.

# 10. Правила достоверности

Запрещено:

- придумывать проценты готовности;
- считать модуль завершённым по имени файла;
- считать тесты пройденными по наличию `SmokeTests.gs`;
- считать архитектуру соответствующей спецификации без проверки зависимостей;
- скрывать неизвестное состояние;
- смешивать Target и Current Architecture;
- использовать старые данные без отметки даты.

Обязательно:

- показывать дату аудита;
- показывать источник статуса;
- показывать уровень уверенности;
- разделять:
  - реализовано;
  - проверено;
  - документировано;
  - используется в рабочей таблице.

# 11. Первый этап реализации

## Этап A — Инвентаризация

1. Распаковать архив проекта.
2. Построить список файлов.
3. Выявить пары `.gs/.js`.
4. Получить список функций.
5. Получить зависимости между функциями и модулями.
6. Получить обращения к листам.
7. Получить обращения к API.
8. Найти использование CacheService, PropertiesService, LockService.
9. Найти тестовые функции.
10. Построить первичный реестр.

## Этап B — Аудит соответствия

Сопоставить:

- спецификация ↔ код;
- модуль ↔ файл;
- лист ↔ модуль;
- требование ↔ тест;
- целевая архитектура ↔ текущая архитектура.

## Этап C — Генерация атласа

Сформировать:

- SVG-карты;
- HTML Mission Control;
- Figma-ready SVG;
- JSON-реестры;
- Markdown-отчёт;
- список задач на рефакторинг.

## Этап D — Figma

1. Создать Figma-файл.
2. Импортировать SVG.
3. Превратить карточки в компоненты.
4. Настроить страницы.
5. Добавить интерактивные переходы.
6. Создать мобильную сводку.
7. Проверить просмотр в приложении Figma на iPhone.

# 12. Definition of Done

Визуальный центр считается реализованным, когда:

- существует Figma-файл `IOS Mission Control`;
- все основные страницы созданы;
- Target и Current Architecture разделены;
- фактические статусы подтверждены аудитом;
- нет выдуманных процентов;
- все модули текущего архива учтены;
- все критические зависимости показаны;
- Roadmap связан с модулями и релизами;
- имеется мобильная навигация;
- доступны SVG, HTML и JSON-реестры;
- обновление атласа можно повторить после изменения кода;
- Codex может использовать реестр как источник для дальнейшей работы.
