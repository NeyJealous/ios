# Investment Operating System (IOS)

# Master Specification v3.0

# 22 --- Code Review Checklist

**Статус:** Канонический регламент проверки изменений

## Назначение

Code Review гарантирует, что каждое изменение соответствует архитектуре
IOS, не ухудшает производительность, не нарушает инвестиционную логику и
сопровождается актуальной документацией.

------------------------------------------------------------------------

# Общие правила

Ни одно изменение не может быть принято без прохождения Code Review.

Проверка обязательна как для изменений, выполненных человеком, так и AI
(Codex и субагентами).

------------------------------------------------------------------------

# 1. Архитектура

Проверить:

-   соблюдение Конституции проекта;
-   отсутствие циклических зависимостей;
-   соблюдение Data Flow;
-   отсутствие новых источников истины;
-   соответствие модульной архитектуре.

------------------------------------------------------------------------

# 2. Производительность

Проверить:

-   нет getRange() в циклах;
-   нет setValue() в циклах;
-   используется getValues()/setValues();
-   применяются Map/Set/Object;
-   отсутствуют лишние API-запросы;
-   используется CacheService;
-   используется LockService при синхронизации.

------------------------------------------------------------------------

# 3. Инвестиционная логика

Проверить:

-   решение проходит через Decision Engine;
-   соблюдается Investment Strategy;
-   нет рекомендаций на 0 рублей;
-   нет рекомендаций с 0 лотов;
-   нет покупки при статусе «Недостаточно данных»;
-   учитываются стратегия счета и резерв.

------------------------------------------------------------------------

# 4. Пользовательский интерфейс

Проверить:

-   интерфейс полностью на русском языке;
-   отсутствуют FIGI, UID, Account_ID, Strategy_ID и другие технические
    идентификаторы;
-   рекомендации объяснимы;
-   даты отображаются в обычном формате;
-   нет технических сообщений пользователю.

------------------------------------------------------------------------

# 5. Документация

Проверить:

-   Master Specification обновлена;
-   Data Dictionary актуален;
-   при необходимости создан ADR;
-   изменён Roadmap (если влияет на план развития);
-   обновлён Project History.

------------------------------------------------------------------------

# 6. Тестирование

Обязательно проверить:

-   Быструю синхронизацию;
-   Полную синхронизацию;
-   Пересчёт рекомендаций;
-   Многосчётную архитектуру;
-   Работу резерва;
-   Купонную лестницу;
-   Ребалансировку.

------------------------------------------------------------------------

# 7. Критические ошибки

Изменение не принимается, если:

-   нарушена архитектура;
-   появились ложные рекомендации;
-   появились циклические зависимости;
-   нарушены источники истины;
-   ухудшилась производительность;
-   нарушен русский пользовательский интерфейс.

------------------------------------------------------------------------

# Итоговая проверка

Перед слиянием изменений необходимо подтвердить:

☐ Архитектура\
☐ Производительность\
☐ Инвестиционная логика\
☐ Пользовательский интерфейс\
☐ Документация\
☐ Тесты\
☐ Отсутствие критических замечаний субагентов

------------------------------------------------------------------------

# Definition of Done

Изменение считается готовым к включению в релиз только после успешного
прохождения всех пунктов данного чек-листа.
