# Investment Operating System (IOS)

# Master Specification v3.0

# 25 --- Release Management

**Статус:** Каноническая спецификация управления релизами

## Назначение

Документ определяет единый порядок подготовки, проверки, выпуска и
сопровождения новых версий Investment Operating System.

Цель --- обеспечить предсказуемые обновления без потери данных
пользователя и без нарушения инвестиционной логики.

------------------------------------------------------------------------

# Основные принципы

1.  Каждый релиз должен быть воспроизводим.
2.  Любой релиз должен иметь возможность отката.
3.  Пользовательские данные являются приоритетом.
4.  Перед выпуском обязательно выполняется полный цикл проверки.
5.  Изменения архитектуры выпускаются только после обновления Master
    Specification.

------------------------------------------------------------------------

# Жизненный цикл релиза

``` text
Backlog
   ↓
Разработка
   ↓
Code Review
   ↓
Тестирование
   ↓
Release Candidate
   ↓
Финальная проверка
   ↓
Релиз
   ↓
Мониторинг
```

------------------------------------------------------------------------

# Типы релизов

## Patch

Исправления ошибок без изменения архитектуры.

Примеры: - исправление расчётов; - исправление отображения; -
исправление синхронизации.

------------------------------------------------------------------------

## Minor

Добавление новой функциональности без нарушения совместимости.

Примеры: - новый аналитический модуль; - новые отчёты; - новые настройки
стратегии.

------------------------------------------------------------------------

## Major

Изменение архитектуры.

Требуется:

-   RFC;
-   ADR;
-   обновление Master Specification;
-   план миграции;
-   регрессионное тестирование.

------------------------------------------------------------------------

# Подготовка релиза

Перед выпуском необходимо:

-   завершить разработку;
-   обновить документацию;
-   выполнить все тесты;
-   проверить производительность;
-   проверить синхронизацию;
-   проверить пользовательский интерфейс.

------------------------------------------------------------------------

# Миграции

Если изменяется структура листов:

-   миграция должна быть автоматической;
-   существующие данные не должны теряться;
-   пользователь должен получить понятное уведомление.

------------------------------------------------------------------------

# Откат

Для каждого релиза должен существовать сценарий отката:

-   восстановление структуры;
-   восстановление настроек;
-   восстановление данных;
-   повторная синхронизация.

------------------------------------------------------------------------

# Release Notes

Каждый релиз сопровождается:

-   номером версии;
-   списком изменений;
-   исправленными ошибками;
-   известными ограничениями;
-   ссылками на ADR и Project History.

------------------------------------------------------------------------

# Definition of Done

Релиз считается успешным, если:

-   все тесты пройдены;
-   отсутствуют критические ошибки;
-   данные пользователей сохранены;
-   документация актуальна;
-   релиз зарегистрирован в Project History.
