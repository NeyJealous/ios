# Investment Operating System (IOS)

# Master Specification v3.0

# 05 --- Project History

**Статус:** Living Engineering Documentation

## Назначение

Project History хранит историю развития Investment Operating System и
объясняет причины ключевых архитектурных решений.

Каждое значимое изменение должно сопровождаться записью в этом документе
и соответствующим ADR.

------------------------------------------------------------------------

# Правила ведения

Для каждого изменения фиксируются:

-   Дата;
-   Версия;
-   Идентификатор записи (PH-XXXX);
-   Название;
-   Причина;
-   Рассмотренные альтернативы;
-   Принятое решение;
-   Последствия;
-   Связанные ADR/RFC;
-   Статус.

------------------------------------------------------------------------

# PH-0001

## Переход к Master Specification

**Причина**

Набор отдельных ТЗ перестал масштабироваться и начал содержать
пересекающиеся требования.

**Решение**

Создать единую Master Specification как главный источник инженерной
документации.

**Последствия**

-   единая документация;
-   упрощение сопровождения;
-   снижение риска противоречий.

------------------------------------------------------------------------

# PH-0002

## Разделение архитектуры на слои

Введены независимые уровни:

-   Providers;
-   Raw Data;
-   Directory;
-   Investment Universe;
-   Facts;
-   Features;
-   Ratings;
-   Decisions;
-   Presentation.

Причина: исключение циклических зависимостей.

------------------------------------------------------------------------

# PH-0003

## Введение Investment Universe

Причина:

Справочник содержит полный перечень инструментов, но не должен
использоваться напрямую инвестиционной логикой.

Решение:

Создать отдельный слой Investment Universe.

------------------------------------------------------------------------

# PH-0004

## Переход к многосчетной архитектуре

Причина:

Необходимость независимых стратегий для разных счетов.

Основные принципы:

-   связь по Account ID;
-   возможность исключения счета из общего портфеля;
-   независимые рекомендации.

------------------------------------------------------------------------

# PH-0005

## Reserve Engine

Причина:

Резерв должен храниться преимущественно в фонде денежного рынка.

Добавлено:

-   целевой резерв;
-   минимальный резерв;
-   расчет покупки по лотам;
-   восстановление резерва.

------------------------------------------------------------------------

# PH-0006

## Coupon Ladder

Причина:

Облигационный портфель должен обеспечивать максимально равномерный
денежный поток.

Добавлено:

-   анализ месяцев выплат;
-   поиск "пустых" месяцев;
-   рекомендации по закрытию календаря купонов.

------------------------------------------------------------------------

# PH-0007

## Development Platform

Принято решение использовать:

-   Codex;
-   MCP;
-   готовых субагентов;
-   собственных специализированных субагентов;
-   Master Specification как источник знаний.

------------------------------------------------------------------------
