# Investment Operating System (IOS)

# Master Specification v3.0

# 23 --- RFC & ADR

**Статус:** Канонический регламент управления изменениями

## Назначение

Документ определяет порядок внесения изменений в Investment Operating
System.

Все архитектурные, функциональные и технические изменения проходят
единый жизненный цикл. Это обеспечивает воспроизводимость решений,
прозрачность разработки и сохранение целостности архитектуры.

------------------------------------------------------------------------

# Основные документы

## Master Specification

Главный источник требований проекта.

Любая реализуемая функциональность должна иметь соответствующее описание
в Master Specification.

------------------------------------------------------------------------

## RFC (Request for Comments)

RFC используется для обсуждения новых возможностей до начала разработки.

RFC обязателен, если изменение:

-   добавляет новый модуль;
-   изменяет архитектуру;
-   изменяет инвестиционную стратегию;
-   влияет на производительность;
-   затрагивает синхронизацию;
-   изменяет модель данных.

### Структура RFC

-   Идентификатор (RFC-XXXX)
-   Название
-   Автор
-   Дата
-   Проблема
-   Предлагаемое решение
-   Альтернативы
-   Анализ преимуществ и недостатков
-   Влияние на архитектуру
-   План внедрения
-   Открытые вопросы

------------------------------------------------------------------------

## ADR (Architecture Decision Record)

ADR фиксирует уже принятое архитектурное решение.

Каждый ADR содержит:

-   ADR-XXXX
-   Название
-   Статус
-   Контекст
-   Рассмотренные варианты
-   Принятое решение
-   Последствия
-   Связанные RFC
-   Связанные разделы Master Specification

ADR не изменяется задним числом. При изменении подхода создаётся новый
ADR.

------------------------------------------------------------------------

# Жизненный цикл изменения

``` text
Идея
  ↓
RFC
  ↓
Обсуждение
  ↓
Утверждение
  ↓
ADR
  ↓
Обновление Master Specification
  ↓
Разработка (Codex)
  ↓
Code Review
  ↓
Тестирование
  ↓
Обновление документации
  ↓
Релиз
  ↓
Запись в Project History
```

------------------------------------------------------------------------

# Требования к реализации

Перед началом разработки необходимо убедиться, что:

-   существует соответствующее требование в Master Specification;
-   при необходимости создан RFC;
-   принято ADR;
-   определены критерии готовности (Definition of Done).

------------------------------------------------------------------------

# Связь документов

Каждое изменение должно иметь двусторонние ссылки:

-   Master Specification ↔ RFC
-   RFC ↔ ADR
-   ADR ↔ Code Review
-   ADR ↔ Project History
-   Project History ↔ Roadmap

Это обеспечивает полную трассируемость решений.

------------------------------------------------------------------------

# Использование Codex

Codex обязан:

-   читать Master Specification перед реализацией;
-   учитывать все связанные ADR;
-   не изменять архитектуру без нового ADR;
-   обновлять документацию вместе с кодом;
-   предлагать RFC при обнаружении архитектурных ограничений.

------------------------------------------------------------------------

# Definition of Done

Изменение считается полностью завершённым только если:

-   код реализован;
-   тесты пройдены;
-   документация обновлена;
-   Master Specification актуальна;
-   Project History дополнена;
-   Code Review успешно завершён.

------------------------------------------------------------------------

# Завершение первого издания

Настоящий документ завершает первое издание Master Specification
Investment Operating System.

Дальнейшее развитие системы осуществляется путём выпуска новых редакций
спецификации, RFC и ADR без нарушения принципов, изложенных в
Конституции проекта.
